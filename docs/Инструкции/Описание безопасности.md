# Описание безопасности

Документ описывает текущую модель безопасности системы: аутентификацию, использование JWT, хранение паролей, роли пользователей и правила доступа к данным. Описание приведено на уровне поведения системы и API-контракта, без привязки к внутренней реализации.

## 1. Общий принцип доступа

Система использует защищенный доступ к данным и операциям. Пользователь должен пройти аутентификацию, после чего получает токен доступа.

Для защищенных методов API клиент передает токен доступа в HTTP-заголовке:

```http
Authorization: Bearer <accessToken>
```

Если токен отсутствует, имеет неверный формат, истек или не может быть проверен, система отклоняет запрос.

## 2. Аутентификация

Аутентификация выполняется по email и паролю.

Пользователь передает учетные данные в систему. Если email существует, пользователь не удален, а пароль соответствует сохраненному паролю, система возвращает данные пользователя и токен доступа.

Если email или пароль неверны, система не раскрывает, какое именно поле введено неправильно. Пользователь получает общую ошибку неверных учетных данных.

## 3. JWT-токен

После успешной аутентификации система выдает JWT-токен доступа.

Токен содержит минимально необходимую информацию для проверки пользователя:

| Данные в токене | Назначение |
| --- | --- |
| Идентификатор пользователя | Определяет, от имени какого пользователя выполняется запрос |
| Роль пользователя | Используется для проверки доступности операций |
| Срок действия | Ограничивает время использования токена |

JWT используется как токен доступа. Клиент должен передавать его при каждом обращении к защищенным методам.

Система не должна использовать данные из токена как единственный источник бизнес-доступа к объектам. После проверки токена система дополнительно проверяет права пользователя на конкретные данные: спортсмена, группу, упражнение, папку или тренировку.

## 4. Хранение паролей

Пароли пользователей не хранятся в открытом виде.

При создании или изменении пароля система сохраняет только хеш пароля. Проверка пароля при входе выполняется путем сравнения введенного пароля с сохраненным хешем.

В ответах API пароль и хеш пароля не возвращаются.

## 5. Ролевая модель

В системе используются три роли:

| Роль | Назначение |
| --- | --- |
| Администратор | Управляет тренерами, пользователями и общей библиотекой упражнений |
| Тренер | Управляет своими спортсменами, группами, упражнениями и тренировками |
| Спортсмен | Просматривает свои тренировки и фиксирует выполнение заданий |

Роль пользователя определяет доступные действия и область видимости данных.

## 6. Правила регистрации пользователей

Создание пользователей ограничено ролевой моделью.

| Кто выполняет действие | Кого может создать |
| --- | --- |
| Первый пользователь системы | Администратора |
| Администратор | Тренера |
| Тренер | Спортсмена |
| Спортсмен | Не может создавать пользователей |

После создания первого администратора регистрация без авторизации недоступна.

## 7. Доступ администратора

Администратор имеет доступ к административным функциям системы.

Администратор может:

- создавать тренеров;
- просматривать пользователей;
- редактировать данные пользователей;
- выполнять мягкое удаление пользователей;
- просматривать и редактировать упражнения в административной области.

Администратор не является участником тренировочного процесса. Он не назначает тренировки спортсменам и не фиксирует результаты выполнения заданий.

## 8. Доступ тренера

Тренер работает только со своей областью данных.

Тренер может:

- создавать и редактировать своих спортсменов;
- выполнять мягкое удаление своих спортсменов;
- создавать и редактировать свои группы;
- добавлять своих спортсменов в группы;
- удалять своих спортсменов из групп;
- создавать, редактировать и удалять свои папки упражнений;
- создавать, редактировать и удалять свои упражнения;
- создавать групповые тренировки для своих групп;
- назначать упражнения спортсменам в рамках тренировки;
- изменять статус тренировок;
- просматривать результаты своих спортсменов.

Тренер не должен получать доступ к:

- спортсменам другого тренера;
- группам другого тренера;
- упражнениям другого тренера, если они не относятся к общей административной библиотеке;
- папкам другого тренера;
- тренировкам другого тренера;
- результатам спортсменов другого тренера.

## 9. Доступ спортсмена

Спортсмен имеет доступ только к своим тренировкам и результатам.

Спортсмен может:

- просматривать назначенные ему тренировки;
- просматривать историю своих тренировок;
- начинать выполнение своей тренировки;
- завершать выполнение своей тренировки;
- начинать, завершать или пропускать задания внутри своей тренировки;
- фиксировать количество попыток и успешных попыток;
- просматривать комментарии тренера, относящиеся к его тренировкам или заданиям.

Спортсмен не должен получать доступ к:

- данным других спортсменов;
- тренировкам других спортсменов;
- результатам других спортсменов;
- управлению группами;
- управлению упражнениями и папками;
- административным действиям.

## 10. Доступ к упражнениям и папкам

Упражнение и папка имеют владельца.

Тренер может изменять только те упражнения и папки, которые принадлежат ему. Упражнения используются при назначении заданий в тренировку.

Если упражнение уже назначено в тренировку, связь задания с упражнением должна сохраняться. Мягкое удаление упражнения не должно разрушать историю назначенных тренировок и результатов.

## 11. Доступ к группам и тренировкам

Группа принадлежит тренеру.

Тренер может создавать и изменять тренировки только для своих групп. При назначении тренировки система должна проверять, что группа и спортсмены относятся к области доступа этого тренера.

Спортсмен получает доступ только к своей персональной части групповой тренировки.

## 12. Защита входных данных

Система должна проверять входные данные для методов API.

Проверяются:

- обязательность полей;
- типы значений;
- допустимые значения статусов и ролей;
- формат email;
- формат дат и времени;
- отсутствие лишних полей в запросе;
- корректность идентификаторов связанных объектов.

Если данные не проходят проверку, система отклоняет запрос и возвращает ошибку валидации.

## 13. Мягкое удаление

Для основных сущностей используется мягкое удаление.

Мягко удаленные данные не должны отображаться в обычных пользовательских списках и не должны использоваться как активные объекты для новых операций.

При этом мягкое удаление не должно нарушать исторические связи уже созданных тренировок, заданий и результатов.

## 14. Ошибки безопасности

Система возвращает ошибку, если:

- пользователь не передал токен доступа;
- токен имеет неверный формат;
- токен недействителен;
- пользователь не имеет роли, необходимой для действия;
- пользователь пытается получить доступ к чужим данным;
- пользователь пытается создать объект с недоступной ролью;
- пользователь передал некорректные входные данные.

Сообщения об ошибках должны быть достаточными для пользователя или frontend-разработчика, но не должны раскрывать чувствительные детали проверки пароля, структуры токена или внутреннего устройства системы.
